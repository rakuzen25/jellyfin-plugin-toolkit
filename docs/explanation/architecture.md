# Foundation architecture

The toolkit is a standard Python package distributed as wheels and source distributions through GitHub Releases. Each plugin is an independent uv project with a committed lockfile and a canonical versioned wheel dependency. uv verifies the locked wheel hash, manages Python and environments, and exposes `uv run jpt`. Toolkit package metadata defines its version; each consumer's .NET plugin version remains separate.

The wheel contains shared data resources. `jpt prepare` copies them to `.build/jpt` so native tools, editors and browser containers can access them through the checkout. Python modules stay in the uv environment. Local commands use normal uv synchronization; CI requires `uv sync --locked` before `uv run --no-sync`.

The standard source boundaries are `src/Core`, `src/Infrastructure`, and `src/Host`. Core owns host-independent policy, models, and effect interfaces. Infrastructure implements storage and external effects. Host owns Jellyfin entity adapters, authenticated APIs, registration, and lifecycle hooks. Plugins declare the allowed dependency graph; omitted layers are valid.

Shared Python modules receive an explicit consumer context. Consumer-dependent task, build, reference-cache, sandbox, and CI functions take `Context` as their first argument; importing a module does not select a consumer. CI derives an immutable `ValidationPolicy` for that context. One Typer command tree parses arguments before selecting the consumer. Its shared console/module boundary accepts `main(argv=None)` without changing process arguments. Typed handlers call ordinary Python operations; only commands that consume configuration load a consumer. Configuration generation only writes bindings; command orchestration owns pin checks. Formatting is a leaf dependency of tasks and checks. Shared tooling must not import consumer application code. Operations that cannot be represented as paths and capabilities remain small plugin-owned adapters. There is no generic inheritance or scripting framework.

Configuration uses strict Pydantic models, exported as `configs/plugin.schema.json` for editors. Python callers use typed attributes such as `ctx.config.frontend.enabled` and `ctx.identity.guid`; `ctx.config.data()` returns declarative inputs for serialization. Tomli-W writes TOML. Each project declares supported dependency ranges and a 24-hour release-age cutoff; uv resolves transitive dependencies into its independent lockfile. Ruff, mypy, and basedpyright belong to the `dev` dependency group. The toolkit owns Python quality policy and check implementations for plugin and standalone repositories. Native configuration inherits shared presets where supported; synchronization materializes mypy policy because mypy has no configuration inheritance. Standalone development consumers can install the toolkit in their `dev` group without making catalog runtime verification depend on it.

Chokidar owns development watching and http-proxy-middleware owns HTTP and WebSocket transport. The toolkit retains source classification, build coordination, successful-response asset substitution, and sandbox deployment. Development queue, watch-policy, and proxy helpers can be imported without generated configuration. Pass configuration explicitly to `sourcePolicy`, `classifyChange`, and `proxyServer`. Node dependencies are restored from each consumer's native lockfile. Remark CLI checks links across documents; a small syntax-tree plugin supplies repository navigation policy.

Optional TypeScript modules cover resource disposal, accessible feedback and native controls. They bundle into each consumer's assets. Navigation, uncertain writes, command serialization and review ownership remain application responsibilities.

Reusable workflows retain a single unconditional `validate` aggregate. Change-aware planning conservatively executes checks when evidence is missing or unusable. Receipts bind enabled checks and toolchain/configuration fingerprints to exact artifact bytes. Publication jobs run protected shared tooling and require authenticated execution; read-only PR jobs receive no publication credentials.

Schema 6 receipts point directly to original successful jobs. Fixture-only browser groups may declare precise inputs: planning builds their assets, fingerprints selected emitted bytes together with tests, fixtures, browser image, execution settings and runner image, and verifies them again before execution. Source provenance remains in the receipt, allowing publication verification without rebuilding. Broader change-selection rules remain independent; unrelated backend or lint changes can select a browser group whose existing result is still reusable. Live-server tests retain ordinary source fingerprints.

Catalog policy independently specifies required checks, artifact profiles, plugin identities and approved signers. A release receipt cannot relax those requirements. Receipts must use the supported schema and satisfy catalog policy.

Lifecycle disposal releases all resources before raising an `AggregateError` for cleanup failures. Repeat disposal remains harmless. Aborting a listener releases its lifecycle ownership, and an already-aborted signal creates no registration.

Shared scripts, actions, configuration presets, and UI components form the common plugin framework. Prefer a toolkit change when an improvement should become standard for plugins using that capability. Plugin-specific application behavior, runtime pins, dependency updates, repository policy, and extensions remain consumer-owned. Changes to reusable optional components justify foundation releases; compatible consumer tool updates do not require one. Toolkit tests use independent synthetic consumers rather than named downstream repositories.

Consumer-native configuration files import presets from `.build/jpt`, retaining editor discovery and local overrides. Trusted synchronization reads a proposed release as data, invokes uv to update its wheel dependency and lockfile, and coordinates recognized immutable workflow references and Renovate presets. It preserves application and repository policy. Release verification uses a separate protected uv project with trusted verifier code and dependencies. Source bundles retain the exact toolkit wheel, matching source distribution and Python lockfile digest; empty-cache reconstruction may require network access.

Toolkit tests own shared infrastructure contracts, using independent synthetic consumers. Consumer tests assert business behavior, application-specific integrations, and plugin-specific packaging promises; ordinary checks and builds exercise integration without a separate framework smoke-test suite. Consumer operations can add `after` commands to standard behavior without copying the standard implementation.
